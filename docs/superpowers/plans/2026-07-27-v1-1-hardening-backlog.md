# V1.1 求职复盘链路加固 Backlog

日期：2026-07-27
状态：V1 首版后的加固规划，不阻塞当前可运行版本

## 当前 V1 基线

当前版本保留并验证以下核心闭环：

- 面试记录手动创建、读取、编辑与列表展示
- AI 复盘前预览、明确确认、取消和一次性 token
- 复盘建议进入待确认区，不自动写入长期资产
- 建议直接接受、编辑 JSON 后接受、忽略
- 接受建议时由主进程严格校验并原子写入
- 复盘审计快照、并发 CAS、合并无变化拒绝
- 显式选择允许发给 AI 的现有资产，默认不选择

本轮已经完成的安全加固包括：token 不保存 API Key、确认时重读设置、同面试只保留最新请求、TTL 与容量限制、取消 IPC、晚到 token 清理、并发请求顺序保护、超大外发快照在调用 AI 前拒绝。

## P1：复盘后锁定面试事实

### 风险与影响

已完成复盘的面试仍可修改日期、录入文字、个人补充和反馈结果。这样会形成“页面上的新事实 + 审计快照中的旧事实 + 无法再次复盘”的分叉，削弱复盘结论的可信度。

### 建议实现

- `InterviewsRepository.update` 使用数据库条件更新：仅允许 `review_snapshot_json IS NULL` 的记录更新。
- 条件更新未命中时区分不存在与已锁定，已锁定返回 `CONFLICT`。
- Renderer 对已复盘记录禁用编辑，并显示：
  “复盘后锁定；如需补充请新建一条面试记录，或在复盘前完善反馈。”
- 不为 `feedbackResult` 留旁路。

### 建议测试

- Repository：复盘后修改任一字段均失败，原字段保持不变。
- 竞态：读取后到更新前刚写入快照，条件更新仍拒绝。
- IPC：绕过 Renderer 直接更新返回安全冲突。
- Renderer：已复盘记录无编辑入口且显示锁定说明。

## P1：坏审计快照与坏建议隔离

### 风险与影响

一条损坏的 `review_snapshot_json` 可能使整个面试列表或岗位详情无法打开；一条损坏的 proposal JSON 可能使整个复盘中心加载失败。宽松 payload schema 还可能给缺失字段补默认值、剥离未知字段，让坏数据冒充有效审计数据。

### 建议实现

- 面试审计状态改为明确的 discriminated union：
  `none | valid | invalid`。
- 无论审计 JSON 是否有效，都返回并展示基础面试事实；坏行只标记“复盘快照损坏”。
- 原始坏 JSON 仅保留在主进程恢复/备份路径，不进入 Renderer DTO，不作为 HTML 渲染。
- proposal 当前格式使用四类完整 strict schema 解码。
- proposal 列表返回 `valid | corrupt` 项或 `{ items, corruptCount }`；坏项只读、不可接受或忽略。
- 单条 `get/accept/ignore` 遇到坏 proposal 时返回安全的 repository 错误，不传播裸 JSON/Zod 异常。
- 旧格式若需兼容，必须通过显式版本迁移处理，不能隐式补默认值。

### 建议测试

- 在生产结构测试数据库中直接写入一条坏快照和一条好快照，列表与岗位详情仍返回两条。
- 坏快照显示 invalid，好快照仍 valid，基础字段可读。
- 混合好坏 proposal 时复盘中心仍展示好项和损坏提示。
- 坏 proposal 不可接受/忽略，不产生资产或版本。
- unknown key 与 missing key 都不得被静默修复。

## P2：四类建议的类型化编辑表单

### 风险与影响

当前“编辑后接受”要求用户直接修改完整 JSON、UUID 数组和 nullable 关联字段。主进程边界是安全的，但普通用户难以使用，也难以定位字段错误。

### 建议实现

- 项目：名称、背景、目标、角色、关键决策、结果、证据、复盘、讲述版本表单。
- 问题：类型、问题文本、回答草稿、出现次数、状态；项目和能力使用本地多选器。
- 能力：名称、JD 频次、证据、缺口、合并目标选择器。
- 心得：标题、内容；岗位、项目、问题、能力使用本地可空选择器。
- 目标类型、操作类型和不可修改的目标上下文只读展示。
- 默认显示类型化表单；JSON 仅作为可选高级视图。
- 使用 Zod 字段级错误，并通过 `aria-describedby` 关联输入项。
- 失败后保留用户输入；取消后下次打开恢复到 proposal 原始值。
- 最终仍提交完整 payload，由主进程 strict schema 再校验。

### 建议测试

- 四种资产各覆盖一条主要编辑成功路径。
- 每种表单至少覆盖一个非法字段和对应可访问性错误。
- 问题/心得的关联选择器提交正确 UUID。
- `occurrenceCount` 非数字、负数和小数均拒绝。
- 失败保值、取消恢复、快速重复点击不重复提交。

## P2：复盘中心移除逐卡 N+1 IPC

### 风险与影响

每张 proposal 卡片分别查询岗位和面试上下文。大量建议会重复查询相同数据，且其中一个查询失败会让两个上下文都显示不可用。

### 建议实现

- 首选由主进程 proposal list 一次返回最小 context DTO：
  `company`、`title`、`interviewRound`、`interviewDate`。
- 不在列表 DTO 中返回 transcript、个人笔记、原始 JD 或审计快照。
- 若暂不改主进程 DTO，可在 ReviewCenter 页面建立按 ID 去重的缓存，并分别处理岗位和面试错误。

### 建议测试

- 渲染多张相同岗位/面试的卡片时不发生逐卡查询。
- context 字段正确且 DTO 不包含 transcript/raw JD。
- 岗位或面试缺失时只影响对应字段，不拖垮 proposal 列表。

## P3：token generation Map 的异常路径清理

### 风险与影响

预览在尚未生成 token 前失败时，`latestPreviewRequest` 可能保留一条
`interviewId -> requestId`。每个面试最多一条，当前影响较小，但长期运行中可进一步收紧生命周期。

### 建议实现

- 在 preview 异常出口按“当前 requestId 仍匹配”条件清理。
- 不能清理更新请求已经写入的 generation。

### 建议测试

- 设置读取失败、输入过大和资产读取失败后，不保留 generation。
- 旧请求失败不得删除后启动请求的 generation。

## P3：补足交互与语义等价测试

### 风险与影响

现有测试已覆盖三类操作成功 toast 和编辑接受失败 toast，但没有分别覆盖直接接受失败、忽略失败和快速双击。Question merge 的无变化测试也未实际覆盖关联数组重排。

### 建议测试

- 直接接受失败和忽略失败各显示对应 toast，proposal 状态不变。
- 同一操作快速重复点击只调用一次 IPC；主进程 CAS 继续作为最终防线。
- Question merge 中使用至少两个关联 ID，数组仅顺序变化时仍视为 no-op。

- 每项遵循 RED → GREEN 的测试驱动流程。
- 聚焦测试、全量测试、TypeScript 类型检查、生产构建、构建产物测试全部通过。
- `git diff --check` 无错误，工作树干净。

## P2：共性能力分析批次审计快照

### 风险与影响

V1 已把所选岗位 ID、模型和能力输出保留在待确认建议中，但当前十二表结构没有独立的“分析批次”元数据位置，无法无损保存同一批次的完整 Prompt、输入与原始输出快照。核心使用链路不受影响，但长期审计与批次级追溯仍可加强。

### 建议实现

- 增加带版本号的 `capability_analysis_runs` 表，保存所选岗位 ID、Prompt、provider origin、模型、输入 JSON、输出 JSON、创建时间。
- `change_proposals` 增加可空的 `analysis_run_id` 外键；同批能力建议共享该批次 ID。
- 确认时在一个数据库事务内写入分析批次和全部待确认建议，任一失败则全部回滚。
- 复盘中心只展示必要来源摘要；完整外发快照默认折叠并按纯文本呈现。
- 为旧数据库提供显式迁移与备份恢复兼容测试。

## P1：Windows 恢复中断与权限故障的人工恢复入口

### 风险与影响

V1 已在替换前生成并校验时间戳回滚副本，重开失败时也会自动回滚；但如果进程在文件替换与自动回滚之间被强制终止，或安全软件持续锁定数据库文件，应用可能无法自行完成恢复。

### 建议实现

- 启动时识别未完成恢复的显式事务标记，并提供“继续恢复 / 使用回滚副本 / 保留现场”三种选择。
- 为 Windows 文件锁、只读目录、磁盘空间不足分别提供可操作的中文诊断，不暴露不必要的绝对路径。
- 对每次替换阶段执行故障注入测试，包括关闭数据库、移动旧库、移动新库、重开和迁移。
- 在恢复失败页提供复制诊断摘要与打开备份目录的用户主动操作。

## P2：回滚副本保留与清理策略

### 风险与影响

V1 成功恢复后会保留带时间戳的回滚副本，避免误恢复后无法找回原数据；长期多次恢复可能积累磁盘占用。

### 建议实现

- 在设置页列出回滚副本的日期、大小和校验状态。
- 默认保留最近 3 份，任何删除都由用户明确确认并采用可恢复删除。
- 清理前再次确认目标位于应用数据目录，拒绝符号链接与目录穿越。
- 增加磁盘空间预检，确保“待恢复副本 + 回滚副本 + 临时文件”可同时落盘。

## P2：大数据库备份进度、取消与更强完整性检查

### 风险与影响

V1 的备份与恢复以忙碌状态阻止重复提交，并使用 SQLite 在线备份与 `quick_check`；数据量很大时，用户暂时看不到页级进度，也不能安全取消。`quick_check` 适合快速验收，但不等价于完整 `integrity_check`。

### 建议实现

- 使用 SQLite backup progress 回调向 Renderer 发送只读进度，不传递文件路径。
- 仅在尚未进入原子替换阶段时允许取消；进入替换阶段后明确显示“正在完成不可中断步骤”。
- 提供可选的深度校验模式，使用 `PRAGMA integrity_check` 并显示预计耗时说明。
- 增加多 GB 数据库、低磁盘空间、目标盘断开和杀进程恢复测试。
